## One player, five websites

Ask a simple scouting question: <mark>is this player cheap for what he produces?</mark> Answering it takes more than one website. FBref has his goals, assists and minutes. Transfermarkt has his market value and every transfer. Understat has the quality of every shot he took. ClubElo and football-data have how strong his club was and how its matches went. StatsBomb and Wyscout have every touch of the ball, for a few seasons.

None of them share an ID for him, and they often don't share a name either. So the question stays unanswered unless someone joins them.

I built a pipeline that does that join. It pulls all five sources, works out which records are the same player, cleans the numbers and loads them into one database. <mark>Every page on the sports site reads from that one database, so two charts can never disagree.</mark> That is what a *single source of truth* means: each fact lives in one place, and everything else reads it from there.

It covers the Big 5 leagues across 18 seasons, about 50,000 player-seasons. Here is the whole thing on one page:

![Diagram of the pipeline in six layers: sources, fetch, build, load, store and serve.](/posts/football-data-was-split/pipeline.svg)

## Five sources, each good at one thing

Each source covers a different slice of the game, and each counts in a different unit. FBref thinks in seasons, Transfermarkt in dates, Understat in shots. <mark>So I took only what each source does best, and decided up front what one row means for every one of them.</mark>

| Source | What I take from it | One row is | How it's fetched |
|---|---|---|---|
| FBref | goals, assists, minutes, tackles, saves | a player's season at one club | a real browser, because the site screens out robots |
| Transfermarkt | market values, transfers, birth dates | a player on a date | an open dataset on Kaggle, scraped by its maintainer, so values can be a few weeks old |
| Understat | xG, xA, every shot with its location | a player's season, or one shot | plain web requests, from 2014 on |
| football-data · ClubElo | match results · club strength ratings | a match · a club on a date | a CSV file · a web request |
| StatsBomb · Wyscout | every on-ball event in a match | one action | open event data, a few full seasons |

That "one row is" column is the most important one. Data engineers call it the *grain*: the thing a single row represents. <mark>Get it wrong and every join after it counts something twice.</mark> A player who moved clubs in January has two FBref rows that season, one per club. Treat that as one row and his goals get attached to the wrong club.

### Event data needs one language

The last row works differently. StatsBomb and Wyscout record every pass, carry, shot and tackle, but they log them in different ways. So I convert both into one shared format called SPADL, using the open-source `socceraction` library. Once every action looks the same, a model can put a value on each one: how much it raised the team's chance of scoring, minus how much it raised the chance of conceding. That value is called VAEP.

Open event data covers 9 full league-seasons: four leagues in 2015/16 from StatsBomb, all five in 2017/18 from Wyscout. I train one model per league-season, because two providers logging the same match differently would make cross-provider comparisons meaningless. The output is about 4,800 small files, one per player, and they get their own storage, covered under serving below. The method gets its own post.

Five sources means five different ways to fail: slow downloads, blocked requests and files that change under you. So the first layer is fetching, and I wanted it boring and repeatable.

## Fetching: boring on purpose

Three problems shaped this layer. Re-downloading a full season is slow. FBref blocks you if you ask too often. And a crash halfway through saving a file leaves a corrupt one behind. <mark>So every source gets exactly one reader, and every reader goes through the same cache.</mark>

A reader is one Python file per source with one job: fetch a dataset and save it to disk as a parquet file, a compact column-based format that loads fast. Adding a new source means adding one new file. Nothing else changes.

Every fetch then goes through one function, and it checks the cache first:

```python
key = cache_key(source, dataset, params)   # hash of what was asked for
if not force and cache_hit(source, key):
    return read_manifest(source, key)       # already have it: no download
```

The cache key is a hash of the request itself: the source, the dataset and the parameters, such as league and season. <mark>The same request always lands on the same file</mark>, so a second run costs nothing. That is a *content-addressed cache*: the address comes from what you asked for, not from a filename someone picked.

Every fetch also writes a *manifest*: a small record that sits next to the data and says what it is.

| Manifest field | Why it's there |
|---|---|
| `source`, `dataset`, `params` | what was asked for, so the file can be traced back to its request |
| `rows`, `cols` | a quick check that a refresh didn't come back empty |
| `date_range` | which dates the data actually covers |
| `fetched_at` | how old it is |
| `path` | where the file lives |

Readers return the manifest, not the data. Downstream steps get a pointer and a description, and only load the rows when they need them. That keeps memory flat even when a table runs past half a million shots.

Three smaller decisions make the layer safe to run again and again:

- **Atomic writes.** Each file is written under a temporary name first, then renamed in one step. A crash leaves the old file or the new one, never half of each.
- **Two kinds of refresh.** `force` rebuilds a derived table from cached sources. `refetch` also re-downloads the sources. Rebuilding after a code change shouldn't mean hitting five websites again.
- **One error type.** Any failure inside a reader is wrapped in one `SoccerhubError` that names the source and dataset, so a failed run tells you where it broke.

Together these make fetching *idempotent*: running it twice leaves things exactly as running it once does. That matters later, when the same pipeline runs on a schedule with nobody watching.

Cached files on disk still aren't a database, though. Next: the shape the data takes when it lands.

## The database: eight tables, one rule

The five sources arrive with five different ideas of what a row is. If the tables don't agree on that, every join after them quietly gives wrong answers. So the database runs on one rule: <mark>every table's primary key is its grain.</mark> The key says exactly what one row is, and the database refuses to store the same thing twice.

![Diagram of the eight tables. player_xref decides each player's Transfermarkt id for player_season. player_season links to transfers and to shots, and feeds age_curve. Shots link to match xG by game. Matches and club Elo share only a club name.](/posts/football-data-was-split/tables.svg)
*Eight tables in three groups. Players and price sit on the left, shot data on the right, clubs and matches below. The pink line is the one join that doesn't work cleanly yet.*

| Table | One row is | Key | Links to | Rows |
|---|---|---|---|---|
| `player_season` | a player's season at one club | league, season, club, name | transfers by `tm_id`, shots by Understat id | ~50k |
| `player_xref` | one matching decision | league, season, club, FBref name | `player_season` | ~51k |
| `transfers` | one move between clubs | `tm_id`, date | `player_season` | ~175k |
| `age_curve` | average value at one age, one position | position, age | built from `player_season` | 76 |
| `shots_understat` | one shot | league, season, shot id | match xG by `game_id` | ~550k |
| `team_match_understat` | one match's xG | league, season, game id | shots | ~22k |
| `matches` | one result | league, season, date, home, away | club Elo, by name only | ~33k |
| `club_elo` | a club's rating on a date | club, league, date | matches, by name only | ~190k |

The same key does a second job when data is loaded. Each table's load step updates a row when its key already exists, and the code pins that key to the table's primary key, so the two can't drift apart:

```python
CONFLICT_KEY_PLAYER_SEASON = "league,season,team,player_name"  # matches 0001 PK
TRANSFERS_CONFLICT_KEY = "tm_id,transfer_date"                 # matches 0002 PK
SHOTS_CONFLICT_KEY = "league,season,shot_id"                   # matches 0010 PK
```

Most keys are made of several plain facts rather than one ID. That is a *composite natural key*, and I used it because no ID covers every source: the FBref data I pull has no player ID at all. League, season, club and name are facts every source agrees on. The rule caught one real collision. Deportivo had two players called Adrián López in 2009, so the key rejected the pair. <mark>Now a duplicate name gets its birth year added, and only the player with more minutes keeps the price match</mark>, because the matching couldn't tell which one Transfermarkt meant.

### The same words in every table

A join only works if both sides use the same labels. FBref writes the 2023/24 season as `2324`, and Understat uses its own code. In this database it is `2023` everywhere: the year the season started. League names are spelled one way in every table. Columns use plain names instead of each source's shorthand, so FBref's `Gls` lands as `goals` and stays that way whichever source adds the next column. <mark>Every table speaks the same language, so any two can be joined without translating first.</mark>

### One wide table for players

`player_season` holds stats, market value and xG for a player-season in a single row, even though they come from three sources. I kept them together because the site reads data straight from the browser, and a player page should take one request, not three requests stitched together on someone's phone. The cost is a wide table that three different pipeline steps write into, which is why their order matters later on.

### Built from the data, not fetched

`age_curve` doesn't come from any source. It is the average market value for each position at each age, worked out from `player_season`. Only players with 450 or more minutes count, and an age needs at least 30 players before it gets a value, so a handful of 16-year-olds can't bend the curve. I store the result, all 76 rows of it, because the public database API doesn't allow averaging queries, and the browser shouldn't average 50,000 rows every time someone opens a player page. That is a *derived table*: computed once per refresh, read many times.

### Growing without breaking

The schema lives in 11 SQL migration files, one per change. <mark>Each one only adds: a new table, or new columns. Nothing is ever renamed or dropped.</mark> `player_season` grew three times this way, adding cleaning columns, then defending and goalkeeping stats, then xG. The site kept working through each change because nothing it already read ever moved. Each new table also gets its public read-only rule in the same file that creates it, so no table exists even for a moment without one.

### No foreign keys, on purpose

A foreign key makes the database reject a row whose partner row doesn't exist yet, such as a transfer for a player who isn't in `player_season`. I left them out for two reasons:

- **Sources load on different days.** Transfers refresh on Mondays and Thursdays, and each league's player stats on its own weekday. A foreign key would reject a transfer that arrived before its player.
- **Coverage is honestly partial.** About 7% of players have no Transfermarkt match, and the transfer feed covers every league in the world, not just the Big 5. Foreign keys would force fake partner rows or block real data.

So tables are joined on shared columns, and the next section is what makes those joins trustworthy. `tm_id` is the column that puts a price next to a performance, and the FBref data doesn't have one.
